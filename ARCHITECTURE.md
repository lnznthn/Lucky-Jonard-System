# Bodega: how the app works

This file describes app and back end 2.7.0 (`VERSION` `2.7.0`, service worker cache `toys-v2.7.0`, `VERSION_` `2.7.0` in `Code.gs`). Release 2.7.0 makes Bodega usable by other shops: one app at the GitHub Pages address serves every shop, and each shop's Google Sheet, with the script inside it, is that shop's back end. The shop's name, address, notes line, currency and logo move from each device into the sheet (the Shop tab, and the logo in Script Properties) and reach every device at its sync; the sheet gets a Bodega menu to set itself up and show its connection code; a copied sheet makes its own key; and the app holds its changes when a shop's sheet runs an older back end than the app needs (see "Shop details and the back end's version"). A live 2.6 sheet is upgraded in place by `setup()`: nothing is wiped (see "Going live with 2.7.0"). Release 2.6.0 redraws the invoice image after the shop's own template (logo at the top right, Condition and Expected arrival columns, payment details at the bottom left, a totals block with SubTotal, Discount, Paid, Shipping Fee and a highlighted Total). Each unit carries a condition beside its cost (MISB, MIB, MOC, CIB, Box damage, Loose complete or Loose; see "Movements and FIFO"), and a sale line shows the condition of the units it takes. Invoices gain a discount (typed as a percentage or an amount) and a shipping fee, and the payment details come from a Payment details tab in the sheet. A live 2.5 sheet is upgraded in place by `setup()`: nothing is wiped (see "Going live with 2.6.0"). Release 2.5.0 moves pre-orders onto the invoice: a line with its Pre-order toggle on is "to follow", owed to the customer, and ships later under the same invoice number. Invoices gain Paid and Balance, Suppliers become a tab, supplier orders become one row per line that can be received in parts, the Orders page becomes Suppliers, and Add inventory can record an order (Ordered) as well as a receipt. The separate pre-order record, the pre-order receipt and the Pre-orders tab are gone. A live 2.4 sheet is upgraded in place by `setup()`: nothing is wiped (see "Going live with 2.5.0"). App 2.4.2 renames Update inventory to Add inventory and makes it the last status tab of the Inventory page instead of a page of its own. App 2.4.1 adds an editable Price column to the review. Release 2.4.0 calls what the app used to call an item a product, gives every unit its own SKU, renames Stock to Inventory and Update stock to Update inventory, removes Category and Reorder at, draws every desktop table in one compact fixed-width style with sort and tickbox filters in the header cells, lets the review set a cost each in place, and lets the side bar fold to icons. It builds on 2.3.0, which tracks every unit on hand with its own cost and sells the oldest first (see "Movements and FIFO") and exports the invoice as a PNG image (see "Invoice image"). A live 2.3 sheet is upgraded in place by `setup()`: nothing is wiped (see "Going live with 2.4.0"). App 2.4.3 gives the desktop New sale lines a Cost each column (the cost of the units the line takes, oldest first, or "Add the cost" when one has none, which opens the product sheet), in place of the no-cost note under the line; the phone keeps the note.

Bodega is a single-page web app (PWA) for a small shop that sells through chat, over a Google Sheet, installed on a phone's home screen. It is local-first: the phone keeps every product and movement, computes stock itself, and uses the sheet to share data between devices and to keep a record the owner can read and chart. This file is the reference for anyone changing the app, so the logic below does not have to be rediscovered from chat history.

This repository is meant to be served by GitHub Pages. Keep the spreadsheet ID, the connection key and real stock data out of this file and out of the code.

It follows the same pattern as the Ledger app (a public Pages repo, an Apps Script web app bound to a sheet, a `URL#key` connection code, a queue of pending writes, paste-to-import).

## Files and deployment

| File | Role |
| --- | --- |
| `index.html` | The whole app: markup, CSS and one main `<script>`. A small `<script data-boot>` in the head applies the stored theme before the first paint. `VERSION` and `APP_NAME` are constants at the top of the main script. |
| `sw.js` | Service worker. The page is network-first (3-second budget, then the cached copy); fonts, icons and the manifest are cache-first. Never caches sheet data. |
| `fonts/` | Bebas Neue 400 and Geist 400, 500 and 600 (latin subsets, woff2), served with the app so text looks the same offline. `fonts/README.md` names the source packages and the licence (SIL OFL 1.1). |
| `manifest.webmanifest`, `icons/` | Home-screen install metadata. |
| `apps-script/Code.gs` | The back end. Paste it into the sheet's Apps Script project; it is not deployed from this repo. |
| `test/` | `mock-backend.js` runs `Code.gs` unchanged against an in-memory fake of Google's services and serves it over HTTP like the `/exec` URL. `backend.test.js` tests `Code.gs` through it directly. The browser tests drive the app in Chrome against it: `e2e.py` (stock, import, sync), `e2e_v2.py` (product details, invoices and the invoice image, returns), `follow.py` (to-follow lines on an invoice: ship, cancel, payments, expected date), `supply.py` (suppliers, supplier orders in Add inventory, receiving per line), `cost.py` (units and cost: FIFO sales, cost changes, deficits, returns, reversals, the "No cost yet" filter), `condition.py` (each unit's condition from stock in to the product sheet and a sale line, the discount and shipping fee, payment details in Settings), `shop.py` (the shop's details through the sheet to a second device, the logo, the one-time move-up with fill, the New shop guide, the version guard), `fix.py` (Correct this row), `desktop.py` (the desktop layout and its tables) and `offline.py` (offline launch). `common.py` holds the helpers they share; importing it resets the mock backend, so each test starts on an empty sheet. They read the ports from `APP_PORT` and `API_PORT` (default 8765 and 8766). |

Changing this repo needs only a push to `main`; GitHub Pages republishes in about a minute. Changing `Code.gs` means pasting the new file into the Apps Script editor and publishing a new version of the existing web app deployment (Deploy > Manage deployments > edit > New version), which keeps the `/exec` URL.

### Release checklist

1. Bump `VERSION` in `index.html`, and `VERSION_` in `Code.gs` when the back end changes.
2. Bump `CACHE` in `sw.js` to the same version (`toys-vX.Y.Z`). Browsers only install a new service worker when the bytes of `sw.js` change.
3. Never commit an empty or truncated `sw.js`: `test -s sw.js && node --check sw.js`.
4. Check the main script parses (the head script is `<script data-boot>`, so `indexOf('<script>')` finds the main one): `node -e "const h=require('fs').readFileSync('index.html','utf8');new Function(h.slice(h.indexOf('<script>')+8,h.lastIndexOf('</script>')))"`.
5. Run the tests as the README lists them: `node test/backend.test.js`, then start `python3 -m http.server 8765` and `node test/mock-backend.js 8766` and run `for t in test/*.py; do python3 $t; done`. A browser test that fails prints `FAIL` lines and exits non-zero.
6. Commit and push to `main`.

## The sheet

Each shop has a spreadsheet of its own with `Code.gs` bound to it; one copy of the app serves every shop, and the connection code decides which sheet a device talks to. `setup()` in `Code.gs` creates thirteen tabs and formats the text columns as plain text, so a Product ID such as `0012`, a phone number such as `+63917...` or a note starting with `=` is stored as typed. It is safe to run again and never deletes data. After pasting a newer `Code.gs`, run it once more so new tabs and columns exist, then publish a new version of the existing deployment. It also writes the `On hand` numbers, writes Browse, puts the Field dropdown on Edits, and sets a warning-only protection on Products, Movements, Customers, Suppliers, Supplier orders, Invoices, Invoice lines and Returns with the description "Used by the app. Sort and filter in the Browse tab; change fields in the Edits tab." A warning-only protection still lets the owner edit; Google Sheets asks first. Inbox, Browse, Edits, Payment details and Shop have no protection.

The sheet has a **Bodega** menu, which `onOpen()` adds each time the sheet is opened, so a new shop is set up without the script editor. **Set up or upgrade this sheet** (`setupFromMenu()`) runs `setup()` and then shows a dialog with what to do next: deploy the web app (Deploy > New deployment > Web app, Execute as Me, Who has access Anyone), or publish a new version after pasting a newer `Code.gs`; show the connection code and paste it into the app; fill the Shop and Payment details tabs. **Show connection code** (`showCode()`) shows the connection code, `<web app URL>#<key>`, in a box to copy, and writes it to the execution log, when `ScriptApp.getService().getUrl()` returns a URL ending in `/exec`. Otherwise it shows the key, the same deployment steps, and to use the menu again. Both dialogs add that the code is the Web app URL from Deploy > Manage deployments followed by `#` and the key, because `getUrl()` does not always return the deployment's own URL (see "Known limits"). Run from the script editor, where there is no sheet to show a dialog on, the two functions only write the execution log. `showKey()` no longer exists.

`setup()` records the spreadsheet's ID in Script Properties (`SHEET_ID`). Copying a spreadsheet copies its bound script, and its Script Properties can come along, so a copy of the template or of another shop's sheet could otherwise answer to the original's key and show its logo. When `SHEET_ID` is set and differs from the ID of the spreadsheet `setup()` runs in, `setup()` treats the sheet as a copy: it makes a new key, deletes the logo (`LOGO_0` ..., `LOGO_N`, `LOGO_REV`) and `moveRev`, and logs that it did. The tabs keep what was copied. A sheet with no `SHEET_ID` yet (a new sheet, or one last set up before 2.7) keeps its key, or gets one when it has none.

`setup()` also upgrades a 2.3 sheet in place, and is safe to run again. It renames the Items tab to Products when there is no Products tab, deletes the `Category` and `Reorder at` columns of Products by their header names when present, writes the current header row on every tab (`SKU` becomes `Product ID` and `Item` becomes `Product`), fills `SKU` on the `In` rows of Movements that lack one, in sheet order, by the rule under "Movements and FIFO", and makes Browse again when its header is not the current one. When it filled any unit SKU it raises `moveRev`, so each phone downloads the movements again.

`setup()` also upgrades a 2.4 sheet to 2.5 in place (`upgrade25_()`), each tab only while it still has its 2.4 header, so a second run changes nothing. Invoices lose `Type` and `Pre-order ID` and get `Paid` = `Total` and `Balance` 0. Invoice lines get `Line` (1 to n per invoice, in sheet order), `Status` `Delivered` and `Delivered on` = the invoice date. Supplier orders has no rows in a 2.4 sheet and only gets its new header. Pre-orders is deleted when it has no rows below the header. Suppliers is made like any other tab, and the Inbox gets its `Supplier` and `Expected` columns.

`setup()` brings a 2.5 sheet to 2.6 by the header rows alone, so it is safe to run again. Movements gains `Condition` (column L, plain text), Invoices gains `Discount` and `Shipping fee` (columns K and L, `#,##0.00`), and Invoice lines gains `Condition` (column N, plain text). Each is a new last column, so no row is read or rewritten: the cells of older rows stay blank and read as `''` (a condition) or 0 (a discount or fee). It also makes the Payment details tab, empty. Nothing is wiped, and `moveRev` is not raised, because no movement row changes.

`setup()` brings a 2.6 sheet to 2.7 the same way. Column H of Products and of Inbox is headed `Product line` in place of `Toy line`; the column does not move and no row is read or rewritten, so the toy-inventory-logger skill, which writes the Inbox by position, is unaffected. It also makes the Shop tab with its four labels and records `SHEET_ID`. Nothing is wiped, the key stays, and `moveRev` is not raised.

`wipeAllData()` starts again from an empty sheet. It is run by hand from the script editor, after every phone has synced with nothing waiting, and takes the script lock so a phone syncing at that moment waits. It first saves a copy of the whole spreadsheet named "Bodega backup" and the date (`Bodega backup 2026-11-17`). It then clears every row under the header on Products, Movements, Customers, Suppliers, Supplier orders, Invoices, Invoice lines, Returns and Edits, deletes the Browse tab, and raises `moveRev`, so each phone drops its movements at its next sync. Invoice numbers restart at 1, because the next number is worked out from the invoices on file. The connection key, the logo, the other tabs, their formatting and protections, the Inbox, Payment details and Shop stay. Browse is deleted rather than cleared because the script owns it: the next write (or `setup()`) makes it again with the current header and text columns, and no filter or format from an older layout is left on it. The app needs no reset button; each phone picks up the empty sheet at its next sync.

`reopenInbox()`, also run by hand and optional, clears `Status` on the Inbox rows marked `Done`, so the rows Claude already researched come back for review and can be applied again with their costs. Only the `Done` cells are cleared; `Dismissed` and `Working` stay.

**Products** (one row per product): `Product ID`, `Name`, `Price`, `Active` (`Yes` or `No`), `On hand`, `Manufacturer`, `Brand`, `Product line` (headed `Toy line` before 2.7), `Character`, `Release date`, `Release check`. The Product ID (`T0001` and so on) is the key of the row and is never shown in the app; Category and Reorder at no longer exist. `On hand` is a plain number that the script writes: after every `add` request that changed movements or products, it works out stock for every product from Movements and writes column E in one call, matched to the Product ID in each row at that moment. Reading ignores column E. `Release date` is a best guess stored as text (`2024`, `2024-07` or `2024-07-15`); `Release check` holds `Verify` while that guess still needs checking. A variant (chase, exclusive colour, reissue) is its own row with its own name and Product ID. Archiving sets `Active` to `No`; rows are never deleted. When a Product ID appears on more than one row, the first row is used and every `sync` and `add` reply carries a warning about it.

**Movements** (the log of stock): `ID`, `Date` (`YYYY-MM-DD`, text), `Product ID`, `Product` (the name at the time, for readability), `Direction` (`In` or `Out`), `Qty` (positive whole number), `Reason`, `Ref`, `Note`, `Unit cost`, `SKU`, `Condition`. Every `In` movement the app or the script writes has `Qty` 1 and that unit's cost and condition, so a stock in of four units writes four rows; an `In` with `Qty` above 1 is still read as that many units sharing its cost and condition. An `Out` is one row with the full quantity. `SKU` (column K) is the unit SKU, `<Product ID>-<n>`, which the script writes on every `In` row it appends; an `Out` row leaves it blank, and so does an `In` with `Qty` above 1 typed by hand, whose units show without one. `Condition` (column L) is the condition of the units of an `In` row, or blank when it was not recorded (every row from before 2.6); on a `Sale` it is the condition of the units the line took, which may be several joined with ` / ` (see "Movements and FIFO"). Stock is replayed from this log first in, first out. Movements are only appended, apart from `Unit cost` and `Condition` on an `In` row, which a `cost` or `cond` entry rewrites while a unit of that row is on hand. A mistake is fixed by a reversing entry.

Reasons and the direction each allows (enforced by the app and by `Code.gs`):

| Reason | Direction | Used for |
| --- | --- | --- |
| Opening, Restock, Return | In only | First stock, deliveries, customer returns |
| Sale, Damaged, Lost | Out only | Sales, write-offs |
| Count, Correction, Other | Either | Photo counts and stock-takes, reversals, anything else |

`Ref` links a movement to what caused it: the movement a `Correction` reverses, the invoice number of a `Sale`, the supplier order ID of the `Restock` that received it, or the return ID of a `Return`. `Unit cost` on an `In` is the cost of that unit (blank when not known yet). On a `Sale` it is the cost of the units the line took, fixed when the invoice was issued, and so is its `Condition`.

**Customers**: `ID`, `Name`, `Contact` (phone or Messenger). Invoices point here by ID and also keep the name and contact as they were at the time.

**Suppliers**: `ID`, `Name`, `Contact`, `Note`.

**Supplier orders** (stock ordered, not yet received; one row per line): `ID` (the line ID, the key), `Order ID`, `Date`, `Supplier ID`, `Supplier`, `Product ID`, `Product`, `Qty`, `Cost each`, `Expected`, `Received qty`, `Status` (`Ordered`, `Received`, `Cancelled`), `Note`. A line can be received in parts; it stays `Ordered` until `Received qty` reaches `Qty`. The rows of one order share its `Order ID`, date, supplier and expected date.

**Invoices**: `No`, `ID`, `Date`, `Customer ID`, `Customer`, `Contact`, `Total`, `Paid`, `Balance`, `Shipping` (blank or `Delivered`), `Discount`, `Shipping fee`. One plain sequential number series. `Total` is the subtotal (the sum of qty × price over the lines that are not `Cancelled`) less `Discount`, never below zero, plus `Shipping fee`, rounded to two decimals; the script works it out in `total_()` and the app the same way. `Discount` is an amount, at most the subtotal when the invoice is issued; the app may have typed it as a percentage, but only the amount is stored. A blank `Discount` or `Shipping fee` reads as 0. `Balance` is `Total` less `Paid`.

**Invoice lines** (one row per line, keyed by `Invoice ID` and `Line`): `Invoice no`, `Invoice ID`, `Line` (1 to n within the invoice), `Product ID`, `Product`, `Qty`, `Listed price`, `Charged price`, `Unit cost`, `Status`, `Expected`, `Order line`, `Delivered on`, `Condition`. `Status` is `Delivered` (the units left stock), `To follow` (owed: no movement and no cost yet) or `Cancelled`. `Expected` and `Order line` say when a to-follow line should arrive and which supplier-order line it waits for. `Delivered on` is the day the units left stock. `Condition` is the condition of the units the line took, as on its `Sale` movement: blank on a to-follow line until it ships, and on lines from before 2.6.

**Returns** (append-only, one row per returned product): `ID`, `Date`, `Invoice no`, `Invoice ID`, `Customer`, `Product ID`, `Product`, `Qty`, `Outcome` (`Restock`, `Write-off`), `Refund`, `Note`.

**Inbox** (rows Claude writes after reading photos): `Added`, `Type` (`Count`, `Receive` or `Order`), `Name`, `Qty`, `Cost each`, `Manufacturer`, `Brand`, `Product line`, `Character`, `Release date`, `Verify`, `Note`, `Status`, `Supplier`, `Expected`. Every column is plain text. Claude appends rows here through the Google Sheets connector, using the toy-inventory-logger skill, after reading photos of boxes, shelves or supplier paperwork. This is the one data tab the app does not write first, and nothing in it counts as stock. `Cost each` is a starting value for every unit the row adds; the owner can overwrite it with the landed cost in Correct this row. A row is waiting when `Name` is filled and `Status` is blank; a row with any `Status` is not sent to the app. The statuses are `Working` (an intake run may set it while it still researches a row, and clears it when the row is ready), `Done` (the app recorded the row) and `Dismissed` (the owner dismissed it). The app sets `Done` only on rows it actually recorded. `Supplier` and `Expected` belong to `Order` rows (a supplier order or quotation). A `Type` starting with O reads as `order`, with R as `receive`; any other value reads as `count`.

**Browse** (for the owner; the app never reads it): `Product ID`, `Name`, `Price`, `Active`, `On hand`, `Incoming`, `Owed`, `Left to promise`, `Units on hand`, `Stock value at cost`, `Units without cost`, `Manufacturer`, `Brand`, `Product line`, `Character`, `Release date`, `Release check`. One row per product, plain values, frozen header. The script owns it: at the end of every `sync` and every `add` it clears everything below the header and writes the tab again in one call, in Products order. The numbers use the app's definitions (see "The four numbers per product" and "Movements and FIFO"). `Units on hand` lists each unit on hand, oldest first, as its SKU, its cost (`?` without one) and its condition when one is recorded (`T0012-3 1200 MIB, T0012-4 ? Loose, T0012-5 900`); a unit without a SKU starts with its cost. `Stock value at cost` is the sum of the known costs of those units, and `Units without cost` counts the rest; all three are blank when no unit is on hand. A basic filter on the tab stays in place. A sort is not kept: the next rewrite puts the rows back in Products order. `setup()` creates the tab, and the first write creates it when it is missing.

**Edits** (product changes typed in the sheet): `Product ID`, `Field`, `New value`, `Status`, `Note`. `Field` has a dropdown with Name, Price, Active, Manufacturer, Brand, Product line, Character, Release date and Release check. At the start of every `sync` and `add`, under the script lock, each row with a Product ID or field and an empty `Status` is applied as an `edit` entry through the same code and checks, before the app's own entries. The script then writes `Status` `Done`, or `Refused` with the reason in `Note`. `Active` takes Yes or No, `Release check` takes Verify or blank, and a blank `Price` clears it. A refused row is not tried again until its `Status` is cleared. The change reaches each phone at its next sync, because the phone reads Products. A cost cannot be changed here.

**Payment details** (typed by the owner): `Method`, `Number`, `Name`, all plain text, one row per way to pay (for example `GCash`, the account number, the account name). `setup()` makes it empty. The app never writes it, it has no protection, and `wipeAllData()` leaves it alone. Every `sync` and `add` reply carries the rows that have a `Method`, in sheet order, as `pay`, and the invoice image draws them. The account numbers therefore live only in the sheet and reach only a device that has the connection code; they are never in this repository. A sheet without the tab (2.6 pasted but `setup()` not yet run) sends `pay` empty and syncs as usual.

**Shop** (the shop's own details, shared by every device of this sheet): `Field`, `Value`, both plain text, one row per field, labelled `Shop name`, `Address`, `Notes` and `Currency` in `Field`. In the JSON they are `name`, `contact`, `foot` and `cur`: the shop name and address at the top of the invoice image, the notes line at its foot, and the currency symbol of every amount; a blank value is `''`. `setup()` makes the tab and writes each label that has no row into a new row after the last one, never touching a `Value`. A row is found by its label, without regard to case or surrounding spaces, wherever it is, and the first row with a label is the one used, so the owner may reorder the rows and type the values. The app sets them with a `shop` entry (see "Sync protocol"). The tab has no protection, `wipeAllData()` leaves it alone, and it is not an app tab. A sheet without it (2.7 pasted but `setup()` not yet run) sends the details blank, and the first `shop` entry makes it.

The logo is not in the sheet, because a cell cannot hold a picture's data. Script Properties keep it as its data URL in chunks of 8,000 characters (a property holds at most 9 KB): `LOGO_0`, `LOGO_1`, and so on, with their count in `LOGO_N` and `LOGO_REV`, a counter raised each time the logo changes (0 before the first). Only a PNG or JPEG data URL (`data:image/png;base64,...` or `data:image/jpeg;base64,...`) of at most 120,000 characters is kept, and `''` removes the logo. The chunks, the count and the counter are written in one call, and chunks left over from a longer logo are deleted after it. Setting the logo the sheet already has changes nothing and leaves `LOGO_REV` as it is. `wipeAllData()` leaves the logo alone; `setup()` deletes it only in a copied sheet.

## How the script writes

The owner may sort, filter or edit any tab while a phone syncs; the script lock only keeps two requests apart. So no write trusts a row number the script read earlier.

1. An `add` (or a `sync` with rows waiting in Edits) first plans every entry in memory, reading each tab once. Each record it changes remembers which entries changed it.
2. Before writing, the script reads the key column of every tab it changes in place: Product ID for Products (without regard to case), the ID for Customers, Suppliers, Supplier orders and Invoices (column B on Invoices), the Invoice ID and Line together for Invoice lines, and the ID in column A for Movements when a `cost` or `cond` entry changes a row there. Returns are only ever appended, and so is Movements apart from those two cells; Invoice lines are appended and their status cells change in place. A record whose key is now missing, or appears more than once, is not written, and every entry in the request that changed it fails with `The <tab> tab was changed in Google Sheets (<key> not found)` or `(<key> appears twice)`, followed by `Nothing was written for this entry; fix the tab and sync again.` The plan is then made again without those entries, so nothing they would have written (an invoice, a movement, a pre-order change) is written anywhere. The app keeps a refused entry and lists it under Activity.
3. Rows changed in place are written first. Just before each write the script reads the key cell of the row it expects; if the key is not there it reads the key column again. Each row is written whole, in one call; on Movements only columns J to L are written (`Unit cost`, `SKU`, `Condition`), with `SKU` written back as the row already holds it. Each Movements row written raises `moveRev` (see "Sync protocol"). If the key has gone at this point, that entry fails the same way and its new rows are left out.
4. New rows are added after the last used row of the key column, worked out at that moment.
5. `On hand` is written for every product (see Products), then the Inbox marks, then the shop's details, then the Edits statuses, then Browse. The shop's details take the last value the request planned for each field: the logo goes to Script Properties, and each other value into the row its label is in at that moment, only when it differs. A label with no row gets one after the last row, and so does every other missing label, blank.

Results for entries are final only after the writes. Inbox marks find a row by its row number and its name, `Added`, `Type` and `Qty`, which the app sends as it received them; when the row has moved, they fall back to the one row with that name, `Added`, `Type` and `Qty`. A mark that finds no row, or finds a row that already has a `Status`, changes nothing and does not fail the entry, so a row edited in the sheet keeps waiting. Edits statuses are found again the same way, by row number, SKU, field and value.

## Documents and what they do to stock

A document never changes stock directly. `Code.gs` writes ordinary movements for it in the same request, so the Movements tab stays the single source of stock.

| Action | Rows written | Stock movement |
| --- | --- | --- |
| Supplier order saved (Add inventory set to Ordered) | Suppliers (when the name is new) and Supplier orders: one `Ordered` row per line | None. Counts as incoming. |
| Supplier order line received (all or part) | `Received qty` goes up; Status `Received` when it reaches `Qty` | One `In` / `Restock` per unit, IDs `rcv-<lineId>-<n>` with n continuing from what was received before, `Ref` = order ID, each with the cost and condition typed for that unit (blank allowed) |
| Rest of a supplier order line cancelled | Status `Cancelled`; what was received stays received | None |
| Sale invoice issued (Sales > New sale) | Invoices with `Discount`, `Shipping fee`, `Total`, `Paid` and `Balance`, and one line per product: a line left in stock is `Delivered` with `Delivered on` = the invoice date and its `Condition`, a line with Pre-order on is `To follow` | `Out` / `Sale` per Delivered line, ID `<invId>-<line>`, `Ref` = invoice number, `Unit cost` and `Condition` = the line's. None for a To follow line. |
| To-follow line shipped | Status `Delivered`, `Unit cost`, `Condition`, `Delivered on` | `Out` / `Sale`, ID `<invId>-<line>`, under the same invoice number, with the FIFO cost and condition when it ships |
| To-follow line cancelled | Status `Cancelled`; `Total` is worked out again from the lines not `Cancelled` with the invoice's `Discount` and `Shipping fee`, `Paid` drops by the refund, `Balance` is recomputed | None |
| Expected arrival of a to-follow line changed | `Expected` and `Order line` | None |
| Payment added | `Paid`, `Balance` | None |
| Marked delivered (or unmarked) | `Shipping` set to `Delivered` or blank | None |
| Return recorded | Returns | `Restock`: one `In` / `Return` per unit, IDs `ret-<retId>-1` ... `-N`, `Ref` = return ID, note `Invoice <no>`, at the `Unit cost` of the first Delivered line of that product on the invoice, and in its `Condition` when that is a single condition (blank otherwise). `Write-off`: none. See `RETURN_STOCK_`. |
| Inbox rows applied or dismissed | `Status` on the Inbox rows: `Done` on the rows that were recorded, `Dismissed` on every row shown when the owner dismisses | None from the marking; applying also queues the normal entries, which write their own movements |

A return applies to Delivered lines only and cannot exceed what the invoice delivered of that product, less what was already returned. The stock effect of each outcome lives in one table, `RETURN_STOCK_` in `Code.gs` and `RETURN_STOCK` in `index.html`; change both together.

### The four numbers per product

`on hand` = stock (units on hand less any deficit; see below). `incoming` = the units still due (`Qty` less `Received qty`) on supplier-order lines still `Ordered`. `owed` = the quantity on invoice lines that are `To follow`. `left to promise` = on hand + incoming − owed; a negative number means more has been promised than supply covers. The product sheet shows that sentence as a muted line under the four numbers, and the Left to promise header of the stock table carries it as a hover hint (`LTP_TEXT`). A to-follow line may be linked to a supplier-order line, but owed counts it either way. A to-follow line counts as ready to ship when the stock on hand covers it, taking lines oldest invoice first (`readyLines()`). Home lists it as a job ("Ship Ana Reyes's to-follow lines") and the invoice sheet shows Ship on it.

`free to sell` = max(on hand, 0) − owed. Incoming stock does not count. The New sale form uses this number to decide whether a line's Pre-order toggle starts on (see "The New sale form" below).

### Movements and FIFO

A Product ID is the identifier of a product, a model that can have many units (it is called `sku` in the code and the sync payload, so the protocol does not change). Each unit has a SKU of its own, `<Product ID>-<n>` (for example `T0012-3`), where n counts the units of that product ever received, in movement-log order, from 1, and is never reused. The SKU is a label only: sales still take the oldest unit first. `unit_()` in `Code.gs` and `live()` in `index.html` apply the same rule: an `In` that already has a SKU keeps it and moves the counter to at least its number; an `In` of `Qty` 1 without one takes the next number; an `In` of `Qty` above 1 without one advances the counter by its quantity and gets none; an `Out` has none. A pending unit not yet synced shows a provisional SKU by the same rule. Each unit on hand is tracked through the `In` movement that brought it in, and that movement holds the unit's cost, SKU and condition. Cost means landed cost, worked out by the owner and typed as one number per unit; the app does not allocate shipping or fees.

A unit's condition sits beside its cost wherever a cost is typed or shown, because each unit has its own. It is one of the values below, or blank when it was not recorded (every unit from before 2.6). `CONDITIONS_` in `Code.gs` and `CONDITIONS` in `index.html` hold the same list in the same order; change both together. The condition belongs to the unit: a sale never overrides it, and changing it means changing the unit (a `cond` entry). The script refuses any other value with `Condition must be one of MISB, MIB, MOC, CIB, Box damage, Loose complete, Loose`.

| Condition | Meaning |
| --- | --- |
| `MISB` | Mint in sealed box: factory sealed |
| `MIB` | Mint in box: opened, unit mint, box included |
| `MOC` | Mint on card: still on its blister card |
| `CIB` | Complete in box: opened or displayed, all parts and the box |
| `Box damage` | Unit fine, box dented, torn or faded |
| `Loose complete` | No box, all parts |
| `Loose` | No box, may be missing parts |

`stockOf_()` in `Code.gs` and `fifo()` in `index.html` replay the log the same way. Change both together. Per Product ID, movements are taken in sheet order (in the app: synced movements, then pending ones in queue order); movement dates are not used. Each Product ID has a queue of units on hand, oldest first (one entry per unit, carrying its movement's ID, cost, SKU and condition), and a deficit that starts at zero.

- An `In` of `Qty` q first covers the deficit (those units are consumed), then puts the rest at the back of the queue.
- An `Out` of `Qty` q removes units from the front of the queue. A `Correction` whose `Ref` is the ID of an `In` first removes that movement's own units while they are on hand, then takes the rest from the front.
- What the queue cannot supply is added to the deficit. Stock is units on hand less the deficit, and one of the two is always zero, so stock below zero means a deficit that the next units to arrive cover first.

The cost of a sale line is the sum of the costs of the units the line removes, divided by its quantity and rounded to two decimals. It is blank when any of those units has no cost, or when the line takes stock below zero. The app works it out from `live()` when the invoice is issued (`costOut()`) and sends it as `lines[].cost`; the script writes it unchanged on the invoice line and the `Sale` movement. Nothing rewrites it later, so a cost typed afterwards changes only units still on hand and never an issued invoice. The invoice screen shows margin as the total less the shipping fee and the cost of the lines ("Margin ₱X"), or "Margin unknown: a product has no cost" when a line has none. Margin is not drawn on the image.

The condition of a sale line is that of the units it removes: their distinct conditions in FIFO order, leaving out blanks, joined with ` / ` (usually a single value such as `MIB`), and blank when none is known (`condOut()` in the app). The app sends it as `lines[].cond` when the invoice is issued and as `cond` on `deliver` when a to-follow line ships. The script checks that every part is in the list and writes it unchanged on the invoice line and its `Sale` movement. A to-follow line has no condition until it ships.

A count that lowers stock and a write-off remove the oldest units, like a sale. Reversing an `In` in Activity writes one `Out` `Correction` with `Ref` = that movement's ID, which takes that receipt's unit back out. Reversing an `Out` writes one `In` `Correction` per unit with `Ref` = the `Out`'s ID, its `Unit cost`, and its `Condition` when that is a single condition (blank otherwise), so the units come back at the cost and condition they left with. A `Restock` return follows the same rule with the first Delivered line of that product on the invoice.

A cost is changed with a `cost` entry and a condition with a `cond` entry (see "Sync protocol"). The script refuses either when the movement is unknown (`Unknown movement`), is not an `In`, or has no unit left on hand after replaying every movement, including those written earlier in the same request: `That unit has already left stock, so its cost can no longer be changed.`, or `... so its condition can no longer be changed.` The value the unit already has is never refused, so a retry after a lost response succeeds even once the unit has been sold.

### Invoice image

The invoice exports as PNG. PNG keeps text sharp, and the image is sent through Facebook Messenger, which compresses whatever it receives. The image is made on the device and never stored: it is redrawn from the invoice record each time, so it can be produced offline and on any device that has synced. The text in it cannot be selected. The shop name, address, notes line, logo and currency symbol are the shop's, kept by its sheet and set in Settings > Shop (see "Shop details and the back end's version"); the image reads this device's copy of them (`prefs.shop`, `prefs.cur`), so it is drawn offline too. The payment details come from the sheet's Payment details tab (`docs.pay`), so they reach only a device that has the connection code and are never in the code.

The layout follows the owner's invoice template. A navy bar runs across the top. The shop name, in red, and its contact lines sit at the top left; the logo, when there is one, sits in a 150 × 150 pt box at the top right. Under them is the title "Invoice" with the invoice number beside it ("No. 12"), because the app renumbers invoices. "Billed To:" at the left gives the customer's name and contact; "Date:" at the right gives the invoice date as M/D/YYYY (11/17/2026).

The table has the columns Item, Condition, Qty, Expected arrival and Total price, and every other row is shaded. Cancelled lines are left out. Condition is the line's `cond`, blank when none is recorded; a combined value such as `MIB / Box damage` puts each condition on its own line. Expected arrival is a to-follow line's expected date (`lineExp()`), or "To follow" when it has none, and is blank on every other line. Total price is quantity × price. A long product name wraps within its column and makes its row taller.

Under the table, the payment details sit at the bottom left, one row per method: method, number and account name. With none, nothing is drawn there. The totals sit at the bottom right: SubTotal (quantity × price of the lines not Cancelled), Discount (`disc`, with a minus sign), Paid and Shipping Fee (`fee`). The labels always show; a value shows only when it is above zero, and Paid only on a part payment. The highlighted Total box under them shows the balance after a part payment and otherwise the invoice total; a long amount shrinks to fit. Below, a rule and "Notes:" carry the notes line; without a notes line neither is drawn. Every amount is written with two decimals (`₱750.00`, as the template writes it) and carries the shop's currency symbol.

`drawDoc()` draws the document on canvases 595 pt wide at scale 2, so each image is 1190 px wide. Its height is cropped to the content. An image is at most 1024 pt (2048 px) tall. A line that would not fit starts the next image, which repeats the bar and the column header; the last line takes the payment details, totals and footer with it. When there are several images, each carries "Page i of N" at its foot. `drawDoc()` is synchronous so the number of images is known during the tap: when a logo is set its box is reserved, and `docPngs()` draws the logo in afterwards, fitted inside the box at no more than one point per logo pixel and flush with the right margin. Colours are literal, so the image is the same in the light and dark themes. `prepImg()` starts making the PNGs when the invoice sheet opens, so the tap itself has nothing to wait for; it draws again only when something drawn has changed, including the discount, the shipping fee and the payment details.

The invoice sheet has **Save image**. For a one-image document it opens a blank tab during the tap, so popup blocking does not apply, then points it at the PNG; when no tab opens, the file downloads instead. For a document with several images, every image downloads and no tab opens. File names are `Invoice-12.png`, with `-1`, `-2` and so on added when there are several images (`imgName()`). **Copy image** sits beside it on phone and desktop when the browser can write images to the clipboard (`canCopyImg`) and the document is one image; it copies the PNG and says "Copied. Paste it into the chat." See `saveImg()` and `copyImg()`.

## Sync protocol

All calls are `POST` to the Apps Script `/exec` URL with a `text/plain` JSON body `{ key, action, ...payload }` (plain text avoids a CORS preflight). Responses are `{ ok, data }` or `{ ok: false, error, auth }`. The connection code the owner pastes is `<exec URL>#<key>`; Bodega > Show connection code in the sheet shows it (`showCode()`). A `GET` of the URL answers `{ ok: true, data: { app: 'Bodega API', version } }`.

| Action | Payload | Returns |
| --- | --- | --- |
| `ping` | none | `{ version }`, used by Settings to test the code and by the app to learn the back end's version before it sends entries |
| `sync` | `have: { rows, lastId, moveRev, logoRev }` | `{ items, moves, rows, lastId, reset, moveRev, syncedAt, custs, sups, orders, invs, rets, inbox, pay, shop, warnings, version, logo? }` |
| `add` | `entries`, `have` | `{ results: [{ id, ok, error, sku?, from?, no?, fromNo? }], sync, warnings }` |

`warnings` is a list of plain sentences about problems the script found in the tabs, for example `Items: SKU T0013 appears on 2 rows. The first is used.` The app shows them on Home as a banner under the two buttons, in the danger colour, and replaces them at every sync; the banner is absent when the list is missing or empty. Results for rows of the Edits tab are never sent to the app.

Products, documents, the waiting `inbox` rows and the payment details are always sent whole (a shop has hundreds of them). Each `inbox` row carries its sheet row number (`row`), `type` (`count`, `receive` or `order`) and the cell values as text, with `supplier` and `expected` on order rows. `orders` are the supplier-order lines, `{ id, orderId, date, supId, sup, sku, name, qty, cost, expected, recQty, status, note }`, each invoice in `invs` carries `disc` and `fee` (numbers, 0 when blank) and `lines` of `{ line, sku, name, qty, list, price, cost, status, expected, orderLine, delivered, cond }` in Line order, and `pay` is a list of `{ method, number, name }`, the rows of Payment details that have a Method, in sheet order. Each movement carries `cond` (`''` when blank) beside `cost` and `unit`. `pres` no longer exists. Movements are incremental: the app says how many movement rows it holds, the ID of the last one and the `moveRev` it holds. If `moveRev` is the script's and the sheet still has that ID at that row, only later rows come back; otherwise everything comes back with `reset: true` and the app replaces its copy. Deleting or moving movement rows in the sheet therefore heals itself at the next sync. `moveRev` is a number in Script Properties. The script raises it for each Movements row a `cost` or `cond` entry writes and in `wipeAllData()`, because an incremental pull would miss a changed row, and it compares it strictly: an app that sends no `have.moveRev` gets every movement. The app keeps the value in `meta`. `setup()` deletes it (back to 0) in a copied sheet.

Every snapshot (the reply to `sync`, and `sync` inside the reply to `add`) carries `version`, the back end's `VERSION_`, as `ping` does, so the app always knows which back end it talks to. The back end accepts the entries of older apps, and an older app ignores the fields it does not know. `shop` is `{ name, contact, foot, cur, logoRev }`: the four values of the Shop tab (`''` when blank, or when the tab is missing) and `LOGO_REV`. `logo` is the logo's data URL, or `''` when there is none, and is sent only when `have.logoRev` differs from `LOGO_REV`, compared strictly, so an app that sends no `have.logoRev` gets it. It is the one large value, and an app that holds the current logo never downloads it again.

`add` entries are applied in order and each is idempotent, so a retry after a lost response changes nothing: a product by SKU and name, everything else by its own ID, and a status change, a cost or the shop's details by carrying the final value. The removed entries are `pre`, `prePay` and `preCancel`, and the old `receive { orderId, ... }` and `order { order: { sku, qty } }` shapes.

| `kind` | Payload | Effect |
| --- | --- | --- |
| `item` | `item`, `auto` | New product |
| `edit` | `sku`, `patch` | Change a product's fields |
| `move` | `move { id, date, sku, dir, qty, reason, ref, note, cost, cond }` | One movement (the script adds the unit `SKU` of an `In`; moves in the payload carry it as `unit`). `cond` is `''` or one condition. The app sends an `In` of N units as N entries with IDs `<id>-1` ... `<id>-N`, each `Qty` 1 with that unit's cost and condition, and the `In` `Correction` that reverses an `Out` with the `Out`'s condition when it is a single one. |
| `cust` | `cust { id, name, contact }` | New customer, or new details for one |
| `supplier` | `supplier { id, name, contact, note }` | New supplier, or new details for one |
| `order` | `order { id, date, supId, expected, note, lines: [{ id, sku, qty, cost }] }` | Supplier order: one `Ordered` row per line; a line ID already on file is skipped. Refused for an unknown supplier or no lines. |
| `receive` | `lineId, date, from, costs, conds` | Receive `costs.length` units of a line, where `from` is the Received qty the app saw. `costs` has one value per unit, a number of zero or more or null for blank; `conds`, parallel to it, has each unit's condition, and a missing or short list leaves the rest blank. One bad value refuses the whole receipt. The script writes `rcv-<lineId>-<from+1>` ... `-<from+n>`, skipping IDs already written, sets Received qty to the larger of its value and `from + n`, and sets Status `Received` when that reaches Qty. It refuses more than is due and a Cancelled line. |
| `orderCancel` | `lineId` | Cancel the rest of a line (the received part stays received); refuses a Received line |
| `invoice` | `invoice { id, no, date, custId, paid, disc, fee, lines: [{ sku, qty, price, cost, cond, follow, expected, orderLine }] }` | One invoice. A line with `follow: true` is To follow (no movement, blank cost and condition) and needs the customer's contact; any other line is Delivered with its `Out` / `Sale` movement; `cost` and `cond` are the line's FIFO cost and condition at issue, written on the line and the movement. `disc` and `fee` are numbers of zero or more, blank or missing for 0; a discount above the subtotal (the sum of qty × price) is refused with `The discount is more than the subtotal`. Total = max(0, subtotal − `disc`) + `fee`. `paid` blank means paid in full; otherwise Paid is `paid`, at most the total. |
| `deliver` | `invId, line, date, cost, cond` | To follow becomes Delivered: writes the Sale movement `<invId>-<line>` with `cost` and `cond`, and sets Unit cost, Condition and Delivered on. A line already Delivered is a no-op. |
| `pay` | `invId, paid` | The new total paid, at most the total |
| `lineCancel` | `invId, line, refund` | To follow becomes Cancelled: Total = max(0, the sum of qty × price over the lines not Cancelled − Discount) + Shipping fee, Paid drops by `refund` (at most Paid), Balance is recomputed |
| `follow` | `invId, line, expected, orderLine` | Change a to-follow line's expected date or supplier-order line |
| `ship` | `invId, ship` (`'Delivered'` or `''`) | Delivered mark on an invoice |
| `ret` | `ret { id, date, invId, sku, qty, outcome, refund, note }` | Return (`outcome` is `Restock` or `Write-off`); applies to Delivered lines only. Restock writes one `In` per unit, `ret-<id>-1` ..., at the cost of the first Delivered line of that product and in its condition when that is a single one |
| `cost` | `moveId, cost` (a number of zero or more, or null to clear it) | `Unit cost` (column J) of an `In` movement with a unit still on hand, found by its ID at write time; raises `moveRev` |
| `cond` | `moveId, cond` (`''` or one condition) | `Condition` (column L) of the same, by the same rules as `cost` |
| `inboxDone` | `rows: [{ row, name, added, type, qty }], mark: 'Done' or 'Dismissed'` | Sets `Status` on Inbox rows that still have a blank `Status`, found as described in "How the script writes" |
| `shop` | `shop { name?, contact?, foot?, cur?, logo? }, fill?` | The shop's details. Each field present is set to its value, trimmed, so a retry changes nothing; a field that is missing or null is left as it is. With `fill: true` a field is set only where the sheet has it blank, as the earlier entries of the same request leave it, and the logo only when none is stored. `name` may be 120 characters, `contact` and `foot` 500, `cur` 4; a longer one is refused with `Shop name is too long`, `Address is too long`, `Notes is too long` or `Currency is too long`. `logo` is `''` or a PNG or JPEG data URL: over 120,000 characters it is refused with `The logo is too large; choose a smaller picture.`, and anything else with `The logo must be a PNG or JPEG picture.` One bad field refuses the whole entry. Planned with the other entries and written after them (see "How the script writes"), so two in one request write the last value of each field once. |

The app queues a `cost` or `cond` entry in place of a pending one of the same kind for the same movement (`qLast()`), so the last value typed wins. `live()` applies pending `cost` and `cond` entries to its copy of the movements before the replay, so a typed cost or a picked condition shows at once while offline.

### Product ID collisions

Auto-generated Product IDs are `T0001`, `T0002`, and so on, picked by the phone from its own list. Two phones that work offline can pick the same next Product ID for different products. Product entries made with a generated Product ID carry `auto: true`. When the sheet finds a different product on that Product ID, it assigns the next free one, applies the rest of the batch (movements and documents alike) to the new Product ID, and returns `{ sku, from }`; the app then renumbers whatever is still in its queue. If the name already exists under another Product ID the entry is treated as the same product, which makes a retry of a renumbered batch safe.

A refused product (for example a name already used by another Product ID) blocks every later entry for that Product ID in the same batch, and the app fails any queued entries for it, so a movement or document can never be credited to a different product that owns the Product ID. Refused entries stay in the queue, listed in Activity with the reason and counted on Home under "Needs you"; deleting a refused product also deletes the entries waiting on it.

### Invoice numbers

The phone picks the next number (highest it knows plus one), so invoices can be issued offline. One phone issues invoices, so the numbers carry no device prefix. If the sheet already holds that number on a different document, it assigns the next free one and returns `{ no, fromNo }`; the app says so, because an image already sent carries the old number and should be sent again.

### Shop details and the back end's version

One app serves every shop, and each shop's sheet is its own back end, so two things the app used to keep per device now come from the sheet: the shop's details, and the version of the back end it talks to.

**Shop details.** The shop name, address, notes line and currency symbol are the sheet's Shop tab, and the logo is kept by the back end (see "The sheet"). The app keeps a copy in `prefs.shop` (`name`, `contact`, `foot`, `logo`) and `prefs.cur`, which the invoice image, `money()` and the Home header read, so they work offline. Every snapshot carries `shop: { name, contact, foot, cur, logoRev }`, and `logo` (a data URL, or '' for none) only when the request's `have.logoRev` differs from the back end's. `applySnapshot()` overwrites the copy from `shop` (a blank currency reads as `₱`), and the logo when `logo` is present, then keeps `logoRev` in `meta`, which every request sends as `have`. While a `shop` entry is still pending it leaves the copy and `meta.logoRev` as they are, so the values typed on this device stand until the entry lands, and the next snapshot after that brings a logo another device changed meanwhile.

Settings > Shop saves with `saveShop()`: the fields whose value differs from the copy go into the copy at once and into one pending `shop` entry (`qShop()`), merged with the fields of a `shop` entry already waiting, so one entry carries every change and the last value of each field wins. Before queuing, it checks the lengths the back end takes (`SHOP_MAX`: shop name 120 characters, address and notes 500, currency 4; the fields also carry them as `maxlength`) and refuses a longer value with a toast such as "Shop name is too long: at most 120 characters.", so the sheet never refuses a save. A new logo saves the group as it is typed; Remove sends `logo: ''`. A device that is not connected keeps the entry until it is, and then sends it like any other. `describe()` names the entry "Shop details".

Before 2.7 each device kept its own details. Once per device, at its first start of 2.7 (`shopUp()`, marked by `prefs.shopUp`), a device whose details hold anything, or whose currency is not `₱`, queues one `shop` entry with `fill: true` and the values it has. The back end sets a field from it only where the sheet's is blank, and the logo only when none is stored, so the first device to sync moves its details up and the others take the sheet's without overwriting them. A logo is sent only as a PNG or JPEG data URL of at most `LOGO_MAX` (120,000) characters: `logoUrl()` draws the picture on white as a JPEG at most 480 px a side, then 360, 240 and 120 px until it fits, and Settings refuses a picture that never does ("That picture is too large for a logo. Choose a smaller one."). The move-up redraws a stored logo the same way when it is too long or of another type.

**The back end's version.** `BACKEND_MIN` (`2.7.0`) is the oldest back end the app sends entries to. `meta.ver` holds the version from the last response: `version` in every snapshot (`sync` and `add`) and in `ping`, '' from a back end older than 2.7, which sends none. Before sending entries, `syncNow()` asks `ping` when `meta.ver` is unknown or older than `BACKEND_MIN` (compared as major.minor.patch numbers, `verLess()`). When the back end is older, the queue is held (`held()`): nothing is sent and nothing is pulled, and the reason shows where a failed sync shows (the sync status reads "Sheet out of date", Settings > Connection and the Apply result give the sentence `heldText()`, a manual sync toasts it) and as the first Home row. Everything else works as it does offline. Every later sync asks `ping` again, so the queue goes as soon as the sheet runs the new back end. With nothing waiting, a pull from an older back end works as before. A newer back end than the app is fine. Test and save takes the version from its `ping`, and a connection code with a different URL or key clears `meta` first: `LOGO_REV` counts per sheet, so two sheets can share a rev with different logos, and the new sheet's movements, logo and version must come whole.

## Tabs and routes

The phone has four tabs in a bottom bar: **Home**, **Inventory**, **Sales** and **Suppliers**. Two routes have no tab: `move` (Stock in and out, one product by hand) and `activity` (the movement log, where a movement can be reversed). While one of them shows, Inventory stays lit, and the header carries a close button in place of Settings that returns to the last tabbed page. Add inventory is not a route: it is the last status tab of Inventory (see "Add inventory"). Stock in and out opens from a product's sheet and from Add inventory. Activity opens from the Activity link on Inventory, from "See all in Activity" on a product's sheet and from the Home row about refused entries.

Tapping **Sales** opens the invoice list, with a **New sale** button at the top. When the New sale form has a product picked (a draft in progress), tapping Sales opens the form instead. The form's close button clears the draft and returns to the list.

In a window 900 px wide or more the same page uses a desktop layout, and the phone layout stays as it is. The tabs move to a side bar on the left, which lists Home, Inventory (with the number of waiting Inbox rows, for example "Inventory · 3"), Sales, Suppliers and Activity. The current page is drawn in the text colour. Pages may be up to 1600 px wide (Home 1160 px, Stock in and out 760 px), and Inventory has no width limit. Lists become tables built by `table()`, which share one style: Inventory, the invoice list under the full-width New sale form, the supplier list and the supplier-order lines on Suppliers, Activity, and each group of an Add inventory review. The style is compact: 13 px text, rows of about 30 px with just enough padding to read, and `table-layout: fixed` with a fixed width per column kind (short text, name, date, number, money; `tableTag()`), so widths never change with the filter, the sort or the rows shown. Long text is cut with an ellipsis and carries the full value as a `title`, and numbers are right-aligned. Sort and filter live in the header cells: clicking the header text sorts by that column and clicking again reverses it (text alphabetically without regard to case, numbers numerically, release dates chronologically, with a year-only or year-month value at the start of its period; blank values sort last in both directions), and a small filter button in a filterable header opens a popover. A sort or a filter redraws only the table body (`redrawTable()`): no page render, no flicker, no change of width, and the popover stays open while ticking. A table scrolls sideways inside its own box when the window is narrower than its columns, and its header row stays in view while it scrolls down. Clicking a row opens its sheet (Correct this row in a review); rows can be reached with Tab and opened with Enter. No cell is editable in a table. Only the Inventory table has column filters (see "Inventory and the product sheet"), and the Add inventory review has editable Cost, Condition and Price cells (see "Importing"). Home shows the numbers and the two buttons beside "Needs you". Sheets open as centred dialogs. `wide()` reads the media query, `render()` runs again when the window crosses the breakpoint, and the rest is CSS in the `min-width:900px` block. Sort and filter choices (`ui.sort`, `ui.tf`) are kept in memory while the app is open and survive a re-render after a sync, and `keepScroll()` keeps each table's scroll position. At this width the side bar can be folded to icons only with the toggle at its top (`navMini`, kept in `prefs` on the device); each icon carries its label as a tooltip, and badges such as the number of waiting Inbox rows still show. Nothing else differs between phone and desktop: the data, queue and sync are the same code.

The header shows the page title. On Home it shows the shop name from Settings when one is set, and the app name otherwise. On the right are the sync status as plain text (a button that syncs now; attention colour while entries wait, danger colour when entries were refused, the last sync failed or the sheet is out of date) and the Settings button.

### Home

`renderHome()` draws, from the top on a phone:

1. The numbers strip, titled "<Month> so far", with three cells: Today, Month and Margin, in whole pesos. Margin counts the delivered lines that have a cost, at quantity × (price − cost), leaves out those without one, and takes each invoice's discount off once one of its lines counts; the shipping fee never counts. Once every line of an invoice has a cost this equals its `marginOf()` (its total less its shipping fee and the cost of its lines), and a to-follow line shipped later only adds to it. It shows "–" when no line sold this month has a cost and carries an asterisk when only some do. Tapping the strip opens the invoice list. One muted line follows only when there is something to say: what the asterisk means, that no product sold has a cost, or the refunds this month.
2. Two buttons: **New sale** and **Add inventory** (which reads "Add inventory · N" when N Inbox rows wait). Add inventory opens Inventory with its Add inventory tab chosen.
3. **Needs you**: one list of jobs in a fixed order, built by `needsRows()`. The badge on the title counts the rows. Each row is phrased as an action and opens the place to do it:
   1. Update the sheet: it runs back end <ver>, this app needs 2.7.0, with how many entries wait (Settings). Shown only while the queue is held for an older back end (see "Shop details and the back end's version").
   2. Fix N entries the sheet refused (Activity).
   3. Ship <Customer>'s to-follow lines, one row per customer, oldest first, with the products, quantities and any balance (opens the invoice). A customer with ready lines on two invoices gets one row for the oldest, which says how many more invoices are ready. When four or more customers have ready lines, a single row "Ship to-follow lines to N customers" opens Sales filtered to To follow.
   4. Review N rows from Claude (Inventory, Add inventory tab).
   5. Order stock for N products promised beyond supply (Inventory, filtered).
   6. Receive N supplier order lines due (expected on or before today), with the first two product names (Suppliers, Orders tab).
   7. Collect ₱X on N invoices (Sales, filtered to Unpaid).
   8. Price N products (Inventory, no price yet).
   9. Add the cost of N units, where N counts the units on hand without a cost across active products (Inventory, no cost yet).
   10. Check N release dates (Inventory, release date to verify).

   The rows that open Inventory set its filter and clear the search and the table's column filters, so the list shows exactly what the row counted. On a phone a list of more than five rows shows the first four and a line "See N more", which then reads "See less". The expanded state is `ui.homeMore`, kept in memory only: it survives a re-render after a sync and resets when Home is entered from the tab bar. A desktop window shows every row. With nothing to do the section says "Nothing needs you." and has no badge.

With no products, Inventory and the New sale form say so and offer **Add a product** and **Add inventory**.

### Inventory and the product sheet

Inventory has a search box (name, brand or character), the status tabs All, Out, Archived and Add inventory (see "Add inventory"), and the filters that Home rows open ("Promised beyond supply", "No price yet", "No cost yet", "Release date to verify"), which show as "Showing only: ..." with "Show all". "No cost yet" lists products with a unit on hand that has no cost. It lists products only: no Product ID or SKU column, and no page lists all units. In the desktop layout it is a table of Name, Manufacturer, Brand, Product line, Character, Release date, Price, On hand, Incoming, Owed, Left to promise, Unit cost and Stock cost, at most 400 rows. Unit cost shows one value when every unit on hand has the same cost, a range such as "1,200 to 1,500" when they differ, and a dash when no unit has a cost; it sorts by its lowest value. Stock cost is the sum of the known costs of the units on hand. Manufacturer, Brand, Product line and Character have a filter button in their header (`openTf()`). Its popover lists every value in use with a tickbox each, with "All" and "None" shortcuts, and nothing ticked means no filter. Release date has a from and a to field in its popover that accept `2024`, `2024-07` or `2024-07-15`. The column filters (`ui.tf`) combine with the search box and the filters above the table.

The product sheet shows the four numbers, the Left to promise sentence, Sell, Order stock (opens Add inventory set to Ordered, with the product as a row), Stock in, Stock out and Edit details, then a section **Units on hand**: one row per unit, oldest first, with its SKU (for example `T0012-3`), the date it came in, its reason (Opening, Restock, Count, Return and so on), an editable cost field and, beside it, the unit's condition as a dropdown (on a phone the two fields sit under the SKU, the condition taking the wider share). A unit with no condition recorded (every unit from before 2.6) shows "—" until one is picked. A unit still waiting to sync shows a provisional SKU by the same rule as the sheet. The first row is marked "Next to leave". A changed cost queues a `cost` entry when the field loses focus (`setUnitCost()`); a condition picked queues a `cond` entry at once (`setConds()`), each in place of a pending one for the same unit. A line under the list gives the cost of stock on hand and, when it applies, "2 units have no cost yet". When stock is below zero the section says "Below zero by N. Units that arrive next cover this first." Activity shows a movement's condition beside its cost: a Condition column in the desktop table and a Condition line in the movement's sheet.

### Cost fields

Every screen that takes stock in shows, for each unit, a cost field and beside it a condition dropdown, labelled "Unit 1 cost" and "Unit 1 condition" and so on (`costFields()`): Stock in on the Move screen, Starting stock on a new product, receiving a supplier-order line, and Correct this row. An Ordered batch has one Cost each per row instead, and no condition. Typing in the first cost field fills every cost field that has not been typed in yet, and the first unit's condition fills every unit whose condition has not been picked. A condition starts as MIB (`NEW_COND`); each option carries its meaning as a title (`condSel()`, from `CONDITIONS`). A cost may be left blank and filled later on the product sheet, where the condition can also be changed. For more than 12 units the screen shows one "Cost each" and one "Condition" and a text button "Different costs per unit" that opens a pair per unit. `readCosts()` and `readConds()` give one value per unit, and `qIns()` writes each unit's `In` with its cost and condition. **Receive all** on a supplier order receives every unit at its line's cost each and as MIB.

### The New sale form

One form, `renderInvForm()`, makes one invoice. Its state is `ui.inv`: customer, contact, date, lines, `paid` ('' means paid in full), `disc` (which discount field was typed last, `pct` or `amt`, and its value) and `fee`. Each product line has its own **Pre-order** toggle (`isFollow()`), stored as the line's `follow` once the owner touches it.

- A line that asks for more than is free to sell (on hand less what other to-follow lines owe) starts with Pre-order on. The owner can turn it off and sell now; stock may then go below zero, with no confirmation. Changing or clearing a picked product starts the line again from that rule.
- A line left off leaves stock at issue, at its FIFO cost and with the condition of the units it takes. A line with Pre-order on is to follow: no stock moves, it counts as owed, and its cost and condition stay blank until it ships. A product may appear on two lines when one is to follow and the other is not; two lines of the same kind are refused with a toast.
- A to-follow line shows **Expected arrival**: a dropdown of the open supplier-order lines of that product (`<expected date> · <supplier>`) plus "Type a date". Picking an order line links the sale line to it, and the date shown follows that order line. The first open line is picked by default; with none, a typed date is stored and can later be swapped for an order line.
- A line that leaves stock now shows **Condition**: a dropdown showing the condition of the units the line will take, the oldest units on hand of its quantity (`condOut()`: their distinct conditions in FIFO order, blanks left out, joined with " / "). It shows "Mixed" when those units differ and "—" when none of them has a condition recorded. The condition belongs to the units, so the sale never overrides it for the invoice: picking one edits those units directly, one `cond` entry per unit (`setLineCond()`), and a toast says "Condition saved on <product>". A to-follow line, and a product with no units on hand, have no dropdown. At issue each line in stock sends `cond` = `condOut()`, and a to-follow line sends ''.
- **Discount %**, **Discount (₱)** and **Shipping fee (₱)** are optional. The two discount fields are linked: typing one fills the other from the current subtotal, and the one typed last decides while the lines change, so a % keeps working out its amount (`discShown()`, `invDisc()`). The totals show Subtotal, Discount and Shipping fee only when there is a discount or a fee, then Total (`subRows()`, `invTotHtml()`). Total = max(0, subtotal − discount) + shipping fee, rounded to two decimals, as `Code.gs` works it out (`totalOf()` replays it). A discount above the subtotal is refused ("The discount is more than the subtotal."). The `invoice` entry carries `disc` (the amount) and `fee`, each rounded to two decimals, 0 when blank.
- **Paid now** shows while any line is to follow; blank means paid in full, and it may not exceed the Total. The form then shows the total and the balance, and the customer's phone or Messenger becomes required. A customer name is required in every case.
- The button reads "Issue invoice no. N" and a muted line says what the tap does ("Takes 1 Toy out of stock, leaves 1 Toy to follow, and opens the invoice."). It queues the `cust` entry when needed and one `invoice` entry, clears the form and opens the invoice. A line whose units have no cost yet shows a muted line with "Add the cost", as before.

On a phone each line's Condition sits under its Quantity and Price, the three discount and fee fields sit in one row under the customer, and the date sits behind one folded line, "Dated today". Typing a quantity that changes a line's Pre-order state or its condition redraws the form and keeps the cursor in the field (`invSig()`).

In the desktop layout the form takes the full width. Customer, Phone or Messenger, Date and Paid now sit in one row at the top. The lines are rows of a table: Product (the picker), a muted stock hint, Pre-order, Quantity, Price each, Cost each, Condition, Amount and a remove button; a to-follow line has its Expected arrival in a row under it. The discount and fee fields, the totals and the issue button sit at the right under the lines. The invoice list is a table under the form, with its search box and the tabs All, Unpaid and To follow (`SALES_FILTERS`): No, Date, Customer (carrying "to follow" and "balance ₱X" tags), Products, Total, Margin, Delivered.

#### The invoice sheet

Each line shows its quantity and price, then its condition when one is recorded, and a to-follow line adds "To follow · expected <date>" (the date of its linked order line when it has one), "ready to ship" when stock covers it, and these actions:

- **Ship** (when ready): queues `deliver` with the FIFO cost and the condition (`condOut()`) of the units it takes at that moment. The units leave stock under the same invoice number and the line then shows "Delivered <date>".
- **Change expected date**: the same dropdown and date as the form; queues `follow`.
- **Cancel**: asks how much is refunded and queues `lineCancel`. The total is worked out again without the line (`totalOf()`), so a discount can take up part of the drop, and the form says how much it drops. Leaving the refund blank refunds what was paid beyond the new total, and nothing when nothing was.

Below the lines are Subtotal, Discount and Shipping fee when there is a discount or a fee, the total, Paid and balance when the balance is above zero, the margin (the total less the shipping fee and the cost of the lines, known once every non-cancelled line has a cost; `marginOf()`), **Add a payment** (the amount received now, blank for the full balance; queues `pay`), the Delivered checkbox, Return, and Save image. Deleting an invoice that has not reached the sheet also drops its queued payments, shipping and line changes.

### Add inventory

The last status tab of Inventory (`ui.filter` `'add'`; `renderImport()` draws it into `#addInv`). It reads "Add inventory · N" when N Inbox rows wait, and it shows in place of the product list or table, with no search box and no Home filter line. The Home button, the Home row about rows from Claude and the Add inventory buttons on the empty Inventory and New sale screens open it; tapping the Inventory tab shows All again, as it does after a Home filter. With Inbox rows waiting it shows them for review (see "Importing"). With none waiting it shows one line on sending Claude photos, then a list of other ways to change stock: "Receive a supplier order (N lines on the way)" when lines are on the way (opens Suppliers), "Add a row" (rows typed by hand, received now or ordered), "One product by hand" (the Move screen with a picker) and "Add a new product", then the folded "Paste a block by hand" section. That section is open by default while no connection code is set. When a sync raises the number of waiting Inbox rows and Add inventory is not on screen (`addOn()`), a toast says "N rows from Claude to review".

Above a Receive review (and above rows typed by hand) sits a **Received now / Ordered** switch (`ordSwitch()`); Count batches have none. Received now works as before. **Ordered** adds Supplier (picked from the supplier list or a new name), Order date and Expected arrival for the whole batch. Applying it queues a `supplier` entry when the name is new, any new products, and one `order` entry with one line per row (product, qty, cost each) and no stock movement (`applyOrder()`). **Add a row** (in a review, and in the list of other ways) opens Correct this row on an empty row; saving adds the row to the review, and a hand-made review keeps its rows when the Inbox changes. **Order stock** on a product's sheet and **New order** on Suppliers open Add inventory set to Ordered, the first with that product as a row.

### Settings

Settings (the sliders button in the header, `openSettings()`) has four groups. **Connection** holds the connection code with Test and save, and Re-download everything; while the queue is held for an older back end its hint gives the reason. While the device is not connected it also shows a short **New shop** guide (`guideHtml()`): make a copy of the Bodega template (`TEMPLATE_URL`; while that is '', create a blank Google Sheet, paste `Code.gs` from `CODE_URL` into Extensions > Apps Script, save and reload the sheet), run Bodega > Set up or upgrade this sheet and approve the permissions past Google's "not verified" warning, deploy a web app (Execute as Me, Who has access Anyone), paste the code from Bodega > Show connection code, and fill in the Shop group and the Payment details tab. **Shop** holds the shop name, the address (one line each), the notes line, the currency symbol and the logo, with a hint that every device on this shop's sheet shares them (before the device is connected: that they are kept here until it is), and **Save shop details** (see "Shop details and the back end's version"). Choosing or removing a logo saves the group at once. The group ends with the **Payment details**, read only: one row per method with its number and account name, from the sheet's Payment details tab (`docs.pay`), which the invoice image draws. They live only in the sheet, so they never appear in the code or on a device without the connection code, and they are changed in the sheet. A hint under them says so; with none it says to add rows (Method, Number, Name) to that tab, and before the sheet is connected it says they arrive once it is (`payHtml()`). **Preferences** holds the theme (see "Theme"), kept per device. **Data** holds the two copies for a spreadsheet, "Products and stock" (the columns of Browse, each unit on hand as its SKU, cost and condition) and "All movements" (the Movements columns, Condition last), and Erase data on this device.

### Theme

Settings > Preferences > Theme offers Device, Light and Dark, stored as `prefs.theme` (`auto`, `light` or `dark`; default `auto`) on the device. There is no theme control in the header. The colour tokens are CSS custom properties: light in `:root`, dark under `@media (prefers-color-scheme: dark)` for `:root:not([data-theme="light"])` and again for `:root[data-theme="dark"]`, each with a matching `color-scheme`. An explicit choice sets `data-theme` on `<html>`; Device removes it. The head script applies the stored choice before the first paint, and `applyTheme()` does the same when the setting changes. Both theme-color metas follow the choice. The invoice image is drawn with literal colours on white, so its bytes are the same in either theme.

### Look

Every rule uses the tokens (`--bg`, `--text`, `--muted`, `--line`, `--field`, `--raise`, `--raise-edge`, `--accent`, `--accent-edge`, `--on-accent`, `--attn`, `--danger`). Yellow (`--accent`) marks only what to act on: the primary button, the badges and counts that need action. Bebas Neue is used for page and sheet titles and for the numbers that are the point of an element; Geist for everything else, at 13, 15 and 16 px, weights 400 to 600. Corners are square. A button has a solid lower layer (`box-shadow: 0 4px 0` of its edge colour) that shrinks when pressed; minor actions are underlined text buttons, and destructive ones are text buttons in the danger colour. Sections (`sec()`) are hairline boxes with the title on the top rule; lists are rows (`row()`) with a title, one muted line, and a chevron or one number on the right, and desktop tables (`table()`) use the same hairline rows. Filters and switches are text tabs underlined when chosen. Icons are inline stroke SVGs (`ICON`). Inputs use 16 px text so iOS does not zoom when one is focused.

## Local state (`localStorage`, prefix `toys.`)

| Key | Contents |
| --- | --- |
| `cfg` | `{ url, key }` |
| `items` | Products as of the last sync |
| `moves` | Movements as of the last sync, in sheet order |
| `docs` | `{ custs, sups, orders, invs, rets, inbox, pay }` as of the last sync; `pay` is the sheet's Payment details rows, `[]` until a sync brings them |
| `meta` | `{ rows, lastId, syncedAt, moveRev }` for the incremental pull, `logoRev` (the rev of the logo this device holds) and `ver` (the back end's version, '' when it sent none) |
| `queue` | Entries not yet confirmed by the sheet; `status` is `pending` or `failed` |
| `prefs` | Current tab (default `home`), `navMini` (the side bar is folded to icons), `theme` (`auto`, `light` or `dark`), this device's copy of the shop's details from the sheet, `shop` (name, contact, foot, logo) and `cur` (the currency symbol), for the invoice image, `money()` and the Home header, and `shopUp` (the one-time move-up of 2.6 details was queued) |

Everything the owner does is written to the queue first and flushed when a connection exists. Without a connection the app works fully on the device; the queue holds everything until the connection code is pasted. `live()` merges synced data with pending entries (failed entries are not counted) and is the only thing the screens read. Inbox rows that have a pending `inboxDone` entry drop out of `live().inbox` at once. Pending `cost` and `cond` entries change their movement before the replay, so a typed cost or a picked condition shows at once while offline. It replays pending documents the way `Code.gs` will apply them, including the movements they write with the same IDs (a received line's `rcv-<lineId>-N`, a delivered line's `<invId>-<line>` and a return's `ret-<retId>-N`), so an invoice issued offline already counts against stock. Each movement it writes carries its condition: a received unit the one picked for it, a Sale movement its line's, and a restocked return the first delivered line's when that is a single condition (`oneCond()`). A pending invoice gets its total, and a pending `lineCancel` its new total, from `totalOf()`; an invoice synced before 2.6 has no discount or fee and reads them as 0. Settings > Connection > Re-download everything clears `meta`, so the next sync sends every movement. The script writes the data tabs only for the app's entries and for rows in Edits; Claude writes the Inbox rows.

## Stock math

`stockOf(sku)` is the stock from the FIFO replay of synced movements plus pending ones (see "Movements and FIFO"). Negative stock is allowed and shown in the danger colour: recording a sale for something that was never counted in should not be blocked at the till. A New sale line that asks for more than is free to sell starts with Pre-order on; turning it off issues the line anyway, with no confirmation, and stock goes below zero. A stock out by hand for more than is on hand still asks for confirmation. There is no low-stock state: a product is flagged only at zero (`out`) or below zero (`neg`), since one unit on hand is normal for collectibles. Category and Reorder at no longer exist anywhere: the app, the sheet, Browse and the Edits dropdown dropped them in 2.4.0.

## Importing

There are two ways in, and both end in the same preview. Nothing is written before the preview is applied. The app has no lookup service: the assistant identifies the product, looks up its details and writes the rows.

**Inbox (the main path).** Claude appends rows to the Inbox tab after reading photos of boxes, shelves or supplier paperwork. The photos reach Claude either attached in chat or uploaded to a Google Drive folder that the skill checks; that part lives in the skill and is outside this repo. Every sync returns the waiting rows as `inbox`. Add inventory shows them at once in the review, one `Type` at a time (the type of the first waiting row, then the next type after those are handled). `Count` rows go through the Count from photo rules and `Receive` rows through the Receive rules below. `Order` rows (a supplier order or quotation) open the Receive review with Ordered selected and Supplier and Expected pre-filled from the first row that has them. The review is kept in memory with a key made of the type and the full content of the waiting rows, so a row edited in the sheet after it was loaded shows as it is now after the next sync. Corrections, ticks and "Use" choices stay for rows whose content did not change. Apply queues the normal entries plus one `inboxDone` entry with `mark: 'Done'` for the rows that were recorded: ticked rows that could be recorded, including a count that already matched stock. Rows that were unticked, rows that need a name, problems and rows with an unknown count stay in the Inbox and come back in the next review. "Dismiss these rows" queues `inboxDone` with `mark: 'Dismissed'` for every row shown and records nothing. When no waiting rows are left after Apply, Inventory shows its All tab.

**The review groups** (`impGroup()`), in this order, each a section titled with its row count:

- **Check these** (open, and foldable like Needs a name): a similar name is on file ("Looks like ..." with a "Use ..." button, unticked), the same new name on more than one Inbox row (shown as "Possibly the same box in two photos" with the total and each source row and count; the rows are summed), a release date marked to verify, a movement that would take stock below zero, or a likely duplicate movement.
- **Ready**: everything else that will be recorded. With more than 8 rows it is folded behind a line that says what it holds, for example "172 new products, 3 count changes, 11 with new details".
- **Needs a name** (folded): rows with an unknown count (`?`, blank or not a whole number) or a name starting with "Unidentified", and other rows that cannot be recorded. They are never recorded as they are.

Each row shows the cost of the units it adds next to its quantity ("at ₱1,200 each", a range when they differ, or "no cost yet"), and the Cost cell of a desktop table is an input: one "cost each" applies to every unit the row adds, and it may be blank (`setRowCost()`). The Condition cell beside it is a dropdown: one condition for every unit the row adds, MIB to start (`setRowCond()`); a row whose units differ shows their conditions, which opens Correct this row. The Price cell is an input too: a typed price overwrites the product's price on Apply, as in Correct this row, and a product on file shows its price as the placeholder (`setRowPrice()`). A row whose units have different costs shows the range and opens Correct this row for per-unit costs. Like Correct this row, the typed cost and the picked condition change the review only. In the desktop layout each group is a table of tick box, Name, status, Count or Qty, Cost, Condition, Price, Manufacturer, Brand, Product line, Character, Release date and Note. The Apply button reads "Apply N changes" (N is the ticked rows) and stays at the bottom of the screen above the tab bar on a phone (`.applybar`, `position: sticky`). The Movements paste keeps one flat list.

**Correcting a row.** Tapping a row's name in a Count or Receive review (clicking the row in a desktop table) opens Correct this row (`openFix()`). It shows every field the row can carry: Name, Count (Qty for Receive), the cost and condition fields, Price, Manufacturer, Brand, Product line, Character, Release date, "Release date still needs checking" and Note, and "Use the existing product ..." when a similar product is on file. There is one cost field and one condition per unit the row adds: the count or quantity for a new product or a Receive row, and the count minus the stock on hand for a Count row on a product on file, so a count that lowers stock shows none. The cost fields start with the row's `Cost each` when Claude supplied one, the conditions with the one picked in the review (MIB unless changed), and both follow the rules in "Cost fields". A field counts as typed when its value differs from what the modal showed. A typed value overwrites what is on file for a product already on file; a field cleared in the modal never erases data, and the name never renames a product on file (it only decides which product the row is). Values that came from the Inbox or a paste and were not typed in the modal keep the import rule: they fill blank fields and never overwrite. Saving changes the review only: the corrected values are what Apply records, and the Inbox row in the sheet stays as Claude wrote it. A row under Needs a name that gets a name and a whole-number count moves to Ready (or to Check these when it still needs a decision).

**After Apply** a sheet stays open until it is closed. It says "Recorded: N new products, N count changes, N products with new details." (receipts in place of count changes for Receive), for an Inbox review "Left in the Inbox: N rows that need a name; N rows you unticked.", and whether the entries have synced or are waiting. It follows the sync while it is open.

**Paste a block by hand (the fallback).** When nothing is waiting, Add inventory offers "Paste a block by hand" with three modes: Count from photo, Receive and Movements. The importers parse pasted text split on tabs (or `|`, or `;`) and queue only the ticked rows. "Copy the prompt and product list for Claude" builds the exact instructions for the current mode plus the catalogue, so existing names are reused.

**Count from photo** (`Name, Count, Price, Note, Manufacturer, Brand, Product line, Character, Release date, Verify`), for photos of boxes or of the stockroom. A count is an absolute quantity. For a product already on file the app records only the difference as a `Count` movement: a count that raises stock adds one `In` per unit, at the costs and conditions set in Correct this row as far as they go and then the row's `Cost each` and condition (`unitCosts()`, `unitConds()`); a count that lowers stock writes one `Out`, which removes the oldest units. A product that is new is created with its details and given one `Opening` movement per unit. Re-pasting the same counts therefore changes nothing. Details in the paste fill blank fields on a product already on file and never overwrite what is there. Products missing from the paste are left alone. Names match after lower-casing and stripping punctuation; a name that is similar but not equal (token overlap of 50% or more) is held back unticked with a "Use ..." button. `?` or a blank count skips the row. A product listed twice in one paste is flagged, and its counts are not added. `Verify` set to `Y` raises the release-date flag. An Inbox `Count` row supplies `Name`, `Qty` (the count), `Cost each`, `Note` and the product details; it has no price. Inbox `Count` rows for the same product (one per photo it appears in) are added into one count before the review, so each box must be photographed once. Rows with no usable count or a name starting with "Unidentified" are kept apart and are not added in. Inbox `Receive` rows are dated on the day they are applied.

**Receive** (`Name, Qty, Cost each, Manufacturer, Brand, Product line, Character, Release date, Verify, Note`), for supplier invoices and packing lists. Each row adds one `Restock` per unit on the "Received on" date, at the row's cost and condition unless others were set in Correct this row. A new product is created first, with the price typed in Correct this row when there is one. When the product has an open supplier-order line, the row receives the oldest one with a `receive` entry, up to what is still due on it, so it stops counting as incoming; units beyond that are a plain Restock. With Ordered selected a row becomes an order line instead and nothing comes into stock.

**Movements** (`Date, Product, In/Out, Qty, Reason, Note`, and an optional seventh column with the cost of each unit for an `In` row): the product can be a name or a Product ID. An `In` row is written one unit per movement, each as MIB. Rows that repeat an existing movement (same date, product, direction, quantity and reason, counting the per-unit rows of one `In` as one movement) come in unticked as likely duplicates; rows that would take stock below zero are flagged but allowed. This mode exists only in the paste box.

## Known limits

- A lost response on `pay` followed by a `lineCancel` on the same invoice can restore the refunded amount when the `pay` is retried, because `pay` carries the new total paid and is accepted while it is at most the total. Known limit; check Paid on the invoice after such a retry.
- Two phones that each create a product with the same name at the same moment, one of them offline, will merge into one product and both opening stocks are added. The log shows both entries, and either can be reversed.
- A Product ID cannot be changed after the product is created.
- An invoice cannot be edited or voided once it has reached the sheet. A wrong one is undone with a return, or by reversing its movement in Activity.
- A cost or a condition cannot be changed once its unit has left stock, and a sale's cost and condition never change after the invoice is issued.
- A movement cell edited in place in the sheet, such as a `Unit cost`, is used by the script at once (Browse, the `cost` check) but reaches a phone only when it next downloads every movement: after a `cost` or `cond` entry from any device, a wipe, or Re-download everything.
- The movement log and all documents live in `localStorage` (about 5 MB), which is enough for tens of thousands of rows. Per-unit `In` rows make the log grow by one row per unit received. Beyond that the app would need IndexedDB.
- The Inbox depends on the assistant writing well-formed rows (a name, a numeric `Qty`, a `Type` of `Count` or `Receive`). A malformed row shows up in the preview as skipped or flagged, and the app cannot fix it. The Inbox has never been exercised against a real sheet or the real Google Sheets connector, only against the test fake.
- The tests run against the mock backend only, so they do not prove behaviour on a real sheet. The fake models protections, data validation, clearing contents and a hook that rearranges rows in the middle of a request.
- A change to a row made in the few milliseconds between the script's check of a key cell and its write to that row is not caught. If an entry changes two rows and the second one has gone by the time it is written, the first stays written.
- `On hand` is written after the other writes; a sort in that moment can put a number on the wrong row until the next `add` writes the column again. Browse and the app are not affected, because they work stock out from Movements.
- Every `sync` and `add` reads all of Movements and rewrites Browse, which takes longer on a sheet with many thousands of movements. A `cost` or `cond` entry makes every device download all movements at its next sync.
- A sort of Browse lasts until the next sync. A filter or a filter view is the way to keep a view.
- The protections are warnings. Google Sheets asks before an edit or a sort on those tabs, and the owner can still go ahead.
- The latin font subsets have no peso sign, so ₱ is drawn with a system font next to Bebas Neue and Geist.
- `ScriptApp.getService().getUrl()`, which Show connection code relies on, has been reported since the V8 runtime to return a `/dev` URL, or an `/exec` URL that is not the deployment's own. The dialog therefore also says where the real Web app URL is; confirm the code it shows on a real sheet.
- A copy is recognised only when the original ran `setup()` from 2.7 on, which records `SHEET_ID`. A copy of a sheet that never did keeps the original's key and logo: run `setup()` on the original before copying it, or delete `KEY` under Project Settings > Script Properties in the copy and run `setup()` there.
- `LOGO_REV` is a counter per sheet, so two sheets can be at the same number with different logos. A device that moves to another sheet's connection code gets that sheet's logo only once it stops sending the old `have.logoRev`.
- Settings cannot be opened from Stock in and out, Activity or the New sale form on a phone, because the close button takes its place there.
- `Code.gs` was tested only against a fake of Google's services. The fake enforces plain-text formatting on the columns that hold free text; the real behaviour of `setup()`, `wipeAllData()` and of every write should be confirmed once on a real sheet.
